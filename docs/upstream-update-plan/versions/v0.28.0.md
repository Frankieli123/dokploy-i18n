# v0.28.0

## 状态

- 优先级：中高
- 状态：已完成模块级拆解，待按批次实施
- 对应范围：`v0.27.1 -> v0.28.0`

## 上游来源

- Release：https://github.com/Dokploy/dokploy/releases/tag/v0.28.0
- Compare：https://github.com/Dokploy/dokploy/compare/v0.27.1...v0.28.0
- 发布时间：2026-02-27

## 总体判断

这是一个**真正意义上的大版本**，不是普通小修：

- 上游改动文件：约 `350` 个
- 官方发布重点：Node 24、patches、ZIP drop + build server、monitoring、Dockerfile path、backup/notification、security、pricing

对我们分叉的判断：

1. **不能整体跟**
2. **不能把依赖升级和功能修复绑在一起**
3. **必须拆成模块逐块评估**

---

## 模块拆解

## 1. 运行时 / 构建链 / 基础依赖

### 上游内容

- Node.js 升级到 `24.4.0`
- pnpm 升级到 `10.22.0`
- 多个 Dockerfile、workflow、依赖版本同步升级
- `better-auth` / `zod` / `trpc-openapi` / `drizzle` 等一轮联动升级

### 对我们项目的影响

- 会同时影响：
  - Dockerfile
  - CI
  - 依赖树
  - 类型推导
  - auth
  - OpenAPI

### 当前本地状态

- 当前仓库已稳定运行在自己的依赖组合上
- 本地已经叠加了：
  - i18n
  - AI / MCP
  - volume backups
  - panel domains
  - OpenAPI 定制

### 结论

- **明确跳过**

### 跳过原因

- 这是地基层升级，不是修一个点
- 风险面太大
- 与 `v0.28.0` 的功能修复不应该同轮处理

## 2. Patches 系统

### 上游内容

- 新增 `patch` 表
- 新增 patch repo / patch service
- 新增 patch editor / create file / edit patch UI
- 部署时加入 `generateApplyPatchesCommand`

### 对我们项目的影响

- 会深入碰撞：
  - 应用部署链路
  - 文件编辑体验
  - 新表迁移
  - 前后端接口

### 当前本地状态

- 当前分叉没有这套 patch 体系
- 当前主线重点不在 patch editor，而在 AI / i18n / 备份 / 管理增强

### 结论

- **已作为高冲突专题落地第一版**

### 当前状态

- 后端骨架已接入
- Application / Compose 服务详情页 `Patches` tab 已接入
- 第一阶段保留：
  - `Application + Compose`
  - `Compose raw` 暂不支持

## 3. Build / Deploy：ZIP drop + Build Server

### 上游内容

- ZIP drop 部署在配置 build server 时，解压到 build server

### 当前本地状态

本地已经有：

- `buildServerId`
- `buildRegistryId`
- `dropBuildPath`
- build server 相关 UI

但当前链路仍存在缺口：

- `dropDeployment -> unzipDrop(zipFile, app)`
- `unzipDrop()` 仍主要按 `app.serverId` 走
- 若应用设置了 `buildServerId`，代码与实际构建机可能错位

### 对我们项目的价值

- 这是对你们**已有 build server 能力的补链路**
- 不是新功能，而是把现有功能做对

### 结论

- **必须吸收**

### 建议实施点

- `packages/server/src/utils/builders/drop.ts`
- 必要时联动核对：
  - `packages/server/src/utils/filesystem/directory.ts`
  - `apps/dokploy/server/api/routers/application.ts`

---

## 4. Build / Deploy：Dockerfile path 可选，默认 `Dockerfile`

### 上游内容

- Dockerfile path 改为可选
- 未填写时默认使用 `"Dockerfile"`

### 当前本地状态

当前前端仍然：

- `apps/dokploy/components/dashboard/application/build/show.tsx`
- 将 `dockerfile` 设为必填

当前后端路径拼接也仍是：

- `packages/server/src/utils/filesystem/directory.ts`
- `dockerfile || ""`

### 对我们项目的价值

- 降低配置成本
- 更符合用户默认预期
- 对标准 Docker 项目更友好

### 结论

- **建议吸收**

### 吸收方式

- 只吸收“Dockerfile 可选 + 默认值”本身
- 不跟随上游同时带来的 resolver / 依赖迁移

---

## 5. Monitoring：图表数据上限 / 内存泄漏

### 上游内容

- chart data 增加上限
- 防止 monitoring 页面内存不断增长

### 当前本地状态

当前：

- `apps/dokploy/components/dashboard/monitoring/free/container/show-free-container-monitoring.tsx`
- `setAcummulativeData` 对 `cpu / memory / block / network / disk` 仍持续 append

### 对我们项目的价值

## 6. Security：更新安全配置后同步重建 middleware

### 上游内容

- `updateSecurityById()` 更新时：
  - 先拿旧 security
  - 找 application
  - 先 remove middleware
  - 再更新数据库
  - 再 create middleware

### 当前本地状态

当前本地：

- `packages/server/src/services/security.ts`
- `updateSecurityById()` 只更新数据库
- 不会同步刷新 Traefik security middleware

### 对我们项目的价值

- 防止“改了安全配置，网关没同步”
- 属于真实行为正确性修复

### 结论

- **必须吸收**

## 对我们项目的吸收排序

## 第一批：直接能优化项目

1. ZIP drop -> build server
2. monitoring 数据上限
3. security 更新同步 middleware
4. Dockerfile path 默认值与可选化

## 第二批：增强可观测性

5. dokploy restart notifications 错误处理
6. volume backup custom notifications

## 第三批：有价值但可后移

7. mount API service type filtering

## 高冲突专题（不跳过）

8. patches
9. pricing / startup plan
10. Node 24 / pnpm 10 / 大依赖升级
11. auth / trusted providers / better-auth
12. OpenAPI / resolver / zod / trpc / drizzle 迁移

## 实施建议

如果按“最小风险 + 最大收益”推进，建议顺序：

1. ZIP drop -> build server
2. monitoring 数据上限
3. security middleware 同步
4. Dockerfile 默认值

## 新策略备注

`v0.28.0` 对我们来说，不再只是“拆出 4~6 个低冲突补丁”。

现在改为两层推进：

1. 先吸收低冲突高价值修复
2. 再把高冲突块单独拆成专题继续吃，不默认跳过

### 高冲突块的统一处理原则

- 不跳过
- 不整体硬并
- 先专题拆解
- 真正实施前先确认
