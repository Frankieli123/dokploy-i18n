# v0.28.0 专题：patches

## 状态

- 类型：高冲突专题
- 来源版本：`v0.28.0`
- 当前结论：已完成第一轮专题拆解并已实施首版落地

## 上游这套 patches 到底是什么

它不是一个“补丁接口”，而是一整套在**构建前改仓库文件**的系统。

工作流大致是：

1. 从 Git 仓库克隆一份 patch repo
2. 在前端文件树里浏览仓库文件
3. 读取文件内容
4. 以“create / update / delete”形式保存 patch 记录到数据库
5. 部署时先 clone repo
6. 再把 patch 写回工作目录
7. 再进入 build

## 上游组成拆解

## 1. 数据层

上游新增：

- `packages/server/src/db/schema/patch.ts`

核心结构：

- `patchId`
- `type`: `create | update | delete`
- `filePath`
- `enabled`
- `content`
- `applicationId | composeId`

约束：

- 同一个 application/compose 下，同一 `filePath` 唯一

## 2. 服务层

上游新增：

- `packages/server/src/services/patch.ts`
- `packages/server/src/services/patch-repo.ts`

### `patch.ts`

负责：

- 创建 patch
- 查询 patch
- 更新 patch
- 删除 patch
- 按文件路径查 patch
- 标记文件删除
- 生成部署前应用 patch 的 shell command

关键函数：

- `createPatch`
- `findPatchById`
- `findPatchesByEntityId`
- `findPatchByFilePath`
- `updatePatch`
- `deletePatch`
- `markPatchForDeletion`
- `generateApplyPatchesCommand`

### `patch-repo.ts`

负责：

- 确保 patch repo 存在
- 克隆代码仓库到专用目录
- 读取目录树
- 读取文件内容
- 清理 patch repos

关键函数：

- `ensurePatchRepo`
- `readPatchRepoDirectory`
- `readPatchRepoFile`
- `cleanPatchRepos`

## 3. 路由层

上游新增：

- `apps/dokploy/server/api/routers/patch.ts`

能力包括：

- `create`
- `one`
- `byEntityId`
- `update`
- `delete`
- `toggleEnabled`
- `ensureRepo`
- `readRepoDirectories`
- `readRepoFile`
- `saveFileAsPatch`
- `markFileForDeletion`

## 4. 部署接入层

上游把 patches 接到了：

- `packages/server/src/services/application.ts`

逻辑是：

- 非 docker source 时
- 在 `getBuildCommand(application)` 之前
- 先执行 `generateApplyPatchesCommand(...)`

这意味着：

- patches 直接进入构建链路
- 不只是“保存草稿”，而是**实际影响最终构建产物**

## 5. 前端层

前端能力包括：

## 和我们项目的冲突面

## 1. 部署链路冲突：高

patches 直接插入：

- clone repo -> apply patch -> build

而我们当前项目已经对部署链路做过多轮增强，尤其有：

- AI
- MCP
- build server
- drop deployment
- volume backup / restore
- 若干自定义日志与行为

所以 patches 不是独立功能，而是会插进我们最敏感的链路。

## 2. 文件编辑体验冲突：中高

上游 patch editor 依赖：

- 文件树
- 文件读取
- CodeEditor
- patch 状态管理

我们当前仓库已有：

- `CodeEditor`
- Traefik 文件编辑
- AI / 面板增强

因此 UI 组件不算完全陌生，但把“代码仓文件编辑”塞进现有应用管理页，冲突会比普通设置页大。

## 3. 数据迁移冲突：中

要引入 patches，至少要新增：

- 新表 `patch`
- schema index 导出
- migration

这个不算最难，但不能跳过。

## 4. 仓库访问模型冲突：中

上游用 `ensurePatchRepo()` 在服务端克隆 repo，再读目录树和文件。

这会碰到我们现有：

- Git provider
- build server
- 权限
- compose / application 双路径

尤其是 application 还有 `buildServerId || serverId` 的分流问题。

## 5. 产品方向冲突：中

patches 的本质是：

- 把“源仓库外的构建前改写”做成平台特性

这对一部分用户很强，但也可能：

- 增加调试复杂度
- 让部署结果更不透明
- 和我们当前想保持的“尽量稳、少副作用”方向有张力

## 这套 patches 能给我们项目带来什么

### 1. 对标准 Git 源应用有吸引力

可以在不改上游仓库的情况下：

- 补配置文件
- 修构建参数
- 新建/覆盖环境示例文件
- 删除不想进入构建的文件

### 2. 对 compose 也有一定价值

可以给 compose 项目做构建前文件修补。

### 3. 对 AI 能形成潜在协同

后续如果我们愿意，可以让 AI：

- 生成 patch
- 审核 patch
- 解释 patch

但这属于更后面的阶段，不是第一轮吸收范围。

## 我对这套 patches 的吸收建议

不建议“一口气全吸收”，建议拆三层。

## 第一层：最小骨架

只做：

1. 新表 `patch`
2. 后端 patch CRUD
3. 部署链路支持 `generateApplyPatchesCommand`
4. 暂不做 repo 浏览器
5. 暂不做完整 patch editor

### 好处

- 先打通“补丁能被应用到构建”这条主链
- UI 可以先用简单表单或 JSON patch 输入
- 风险最小

### 风险

- 用户体验一般
- patch 管理不够直观

## 第二层：仓库读取能力

再补：

1. `ensurePatchRepo`
2. `readPatchRepoDirectory`
3. `readPatchRepoFile`

### 好处

- 后端具备“浏览 repo 文件”的能力
- 但前端可以仍保持简化

## 第三层：完整前端体验

最后再补：

1. `show-patches`
2. `patch-editor`
3. `create-file-dialog`
4. `edit-patch-dialog`
5. 文件树交互

---

## 对我们项目的推荐策略

### 推荐：只先吃第一层

原因：

1. 最小侵入
2. 能验证 patches 对我们项目是否真的有价值
3. 不会一下子把前端和部署链路同时搅复杂

### 不推荐：直接全量照搬

原因：

1. 改动面太大
2. 和当前项目主线冲突太多
3. 很容易在 UI、部署、repo 权限三个地方同时出问题

---

## 如果要开始做，建议顺序

1. 先做 `v0.28.0` 第一批低冲突修复
   - ZIP drop -> build server
   - monitoring 数据上限
   - security middleware 同步
   - Dockerfile 默认值

2. 再开 patches 第一层骨架
   - patch schema + migration
   - patch service
   - deploy integration

3. 验证骨架是否值得继续

4. 再决定要不要做 repo browser 和 patch editor

---

## 当前结论

### patches 不该跳过

但也**不该直接整套照搬**。

### 最合理的做法

把它改造成：

- **第一层：先吸收骨架**
- **第二层：再决定是否补全体验**
